# 12｜常见问题排查

排错时先区分失败发生在哪一层：环境、数据、模型配置、单卡训练、DDP、恢复、采样或外部 API。
不要看到任务没输出就立即归因于 GPU，也不要看到 hostname 可达就认为 API 路径正确。

## 最小诊断信息

遇到问题时先保存下面的输出：

```bash
git rev-parse HEAD
git status --short
which python
python --version
python - <<'PY'
import torch
print(torch.__version__, torch.version.cuda, torch.cuda.is_available())
print([torch.cuda.get_device_name(i) for i in range(torch.cuda.device_count())])
PY
nvidia-smi
nvidia-smi topo -m
```

然后记录完整命令、输出目录和第一条真正的 traceback。只说“训练失败”通常不足以定位。

## 安装与 import

### `ModuleNotFoundError`

确认从仓库根目录运行，并使用同一个 Python 安装 editable package：

```bash
pwd
python -m pip install -e ".[data,eval,viz,dev]"
python -c "import config, model, diffusion"
```

使用 `python scripts/...` 时，部分脚本会主动把仓库根加入 `sys.path`；核心入口仍建议从根目录
执行。

### Ruff 或测试版本不一致

```bash
python -m pip install -e ".[dev]"
python -m pytest
python -m ruff check .
```

始终使用 `python -m`，避免 shell 中的 `pytest` 来自另一个环境。

## 数据问题

### `missing manifest`

正式配置默认需要：

```text
data/tinystories-gpt2/manifest.json
```

运行 `python scripts/prepare_tinystories.py`，或使用 `--data` 指向正确 manifest。不要把 mini
subset 假装成正式数据。

### `model vocab_size != tokenizer vocab_size`

配置与 manifest 使用了不同 tokenizer。检查两者的 `vocab_size`，不要通过随意修改一个数字来
绕过。embedding 和输出层必须与 token ids 一致。

### 数据读取出现越界或损坏

检查每个分片的实际字节数是否等于 manifest tokens × 2，并重新计算可疑文件 SHA-256。复制数据
时应整体复制 manifest 与 split 目录。

## CUDA 与显存

### CUDA OOM

按这个顺序调整：

1. 确认没有其他进程占用显存；
2. 降低 `--batch-size`；
3. 增加 `--gradient-accumulation-steps` 保持全局 batch；
4. 保持 BF16；
5. 确认 `gradient_checkpointing=True`；
6. 用较小上下文做流程检查。

不要先改模型层数再声称仍在复现 106M 实验。结构变化应使用新实验名称和报告。

### 显存很高但 `nvidia-smi` 与报告数字不同

报告的 `peak_memory_mb` 使用 PyTorch `max_memory_allocated`，不包含 CUDA context、allocator
reserved 但未 allocated 的空间，以及其他进程。`nvidia-smi` 是设备层总占用，两者口径不同。

### BF16 报错

检查 `torch.cuda.is_bf16_supported()`。旧 GPU 可以改用 FP16 或 FP32；记录精度变化，因为吞吐、
显存和数值稳定性都会改变。

## 训练数值问题

### loss 变成 NaN

检查：

- 学习率是否被异常覆盖；
- 输入 token ids 是否落在词表范围；
- FP16 scaler 是否启用；
- grad norm 在 NaN 前是否突然升高；
- checkpoint 与当前模型配置是否匹配。

先用相同 seed、较小 batch 和 FP32 做几步定位，不要直接删除 checkpoint 重新碰运气。

### MDLM 偶尔没有 target

`corrupt_tokens` 已保证每条序列至少一个 mask。如果自己改写 corruption，应保留这个约束，否则
空 target 会让交叉熵无定义。

### AR loss 和 MDLM loss 哪个更低

不要用这个问题判断胜负。它们对应不同条件分布和 target sampling。分别查看 AR perplexity、
MDLM 固定 mask-ratio accuracy，再使用同 prompt 生成评测。

## DDP 与 NCCL

### 只有一张卡工作

检查命令是否真的包含 `--nproc_per_node=4`，以及 `CUDA_VISIBLE_DEVICES` 是否只暴露一张卡。
查看每个进程的 `LOCAL_RANK` 与 `nvidia-smi` PID。

### NCCL timeout 或 collective hang

常见原因：

- 某个 rank 先 OOM 或抛异常，其他 rank 等待 collective；
- GPU 数量与 nproc 不一致；
- 多个任务争用同一组 GPU；
- 容器网络或共享内存配置异常；
- 某个 rank 的数据或文件路径不可访问。

先向上找第一个 rank 的 traceback。调试时可启用：

```bash
NCCL_DEBUG=INFO TORCH_DISTRIBUTED_DEBUG=DETAIL \
python -m torch.distributed.run --standalone --nproc_per_node=4 train.py ...
```

详细日志很大，只在定位时启用。

### DDP 比单卡还慢

确认比较的是相同全局 tokens，而不是相同步数；增加每卡 batch 以摊薄 all-reduce；检查拓扑是否
跨 NUMA 或 SYS；减少过于频繁的 evaluation。DDP 不保证线性加速。

## checkpoint 与恢复

### `checkpoint model configuration does not match`

当前配置的模型结构与 checkpoint 不同。检查 objective、vocab、block size、层数、头数、隐藏
维度、mask token 和 time conditioning。

### `exact resume requires the same world_size`

原运行和当前 GPU 进程数不同。若目标是精确续训，使用原 world size；若只想迁移模型权重，
应当实现并记录新的 warm-start 流程，而不是绕过检查。

### 恢复后 step 回退

`--resume` 使用 `last.pt`，而不是 console.log 最后一行。异常终止后，最近尚未 checkpoint 的 step
需要重跑，这是预期行为。

## 采样问题

### `sequence exceeds block_size`

prompt 长度加输出长度超过模型上下文。缩短 prompt 或 `--length`。当前 absolute position
embedding 不能静默扩展。

### 字符 prompt 报 KeyError

prompt 含训练词表未出现字符。查看输出目录 `meta.json` 中的 `stoi`。

### MDLM 文本重复严重

先确认 checkpoint 训练充分，再比较 steps 8、16、32、64。增加 steps 可能改善，但当前基线仍
容易重复。不要通过只挑好样本掩盖整体分布，应使用固定 prompts 与批量统计。

### 固定 seed 仍得到不同结果

确认 checkpoint、precision、batching、top-k、temperature 和代码 commit 都相同。正式评测为
每个样本使用独立 generator，普通手动采样还可能受到 CUDA kernel determinism 影响。

## tmux 与日志

### attach 后 pane 是空的

可能是程序暂时不打印、输出通过 pipe 被缓冲，或者 shell 已返回。用以下证据判断：

```bash
tmux list-panes -a -F '#S:#I.#P #{pane_pid} #{pane_current_command} #{pane_dead}'
ps -eo pid,etimes,cmd | rg 'train.py|benchmark_generation.py'
tail -50 path/to/console.log
nvidia-smi
```

### `tmux a -t ...` 立即退出

会话可能已结束。执行 `tmux list-sessions`。如果任务正常完成，应检查结果文件；如果异常结束，
检查日志末尾 traceback，而不是反复 attach。

## 外部 judge API

### 401 或认证失败

确认环境变量存在但不要打印值：

```bash
if [[ -n "${DEEPSEEK_API_KEY:-}" ]]; then echo present; else echo missing; fi
```

检查 base URL 与 model ID。不要把 key 写进 Git tracked `.env`。

### 429 或暂时网络失败

降低 `--concurrency`，保留已有 JSONL 后重新运行。judge 根据 `pair_id` 跳过完成项，不会重复
全部请求。

### 返回不是合法 JSON

脚本请求 JSON object 并验证 schema，失败会指数退避重试。若持续失败，保存错误类型、requested
model 和 provider 返回 model，确认 API 是否仍支持当前参数。

## Git 中看不到输出目录

这是正常设计。`out/`、checkpoint、raw generations 和 API responses 体积大且属于本机产物。
提交的是配置、代码、精简 JSON、报告和图片。不要用 `git add -f out/...` 强行上传模型权重。

## 完成检查

- 遇到问题时能够先确定属于环境、数据、训练、DDP、恢复、采样或 API 哪一层；
- 能收集 commit、Python、PyTorch、CUDA、GPU、拓扑和完整命令；
- 知道降低 batch 后如何用梯度累积保持全局 token budget；
- 知道 raw output 被 Git 忽略是正常现象。
