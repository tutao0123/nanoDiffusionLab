# 03｜从文本到训练批次

语言模型看到的不是字符串，而是整数张量。这一章解释字符数据和 GPT-2 BPE 数据如何变成
`[B, T]` 形状的 batch，以及为什么数据读取方式会影响内存占用和实验公平性。

## 先统一三个符号

教程后面始终使用：

- `B`：batch size，一次送入模型的序列数量；
- `T`：sequence length 或 block size，每条序列的词元数量；
- `V`：vocabulary size，模型能够预测的正常词元数量。

`data.batch(...)` 返回 `torch.long` 张量 `[B, T]`。每个整数都是词表中的编号，而不是字符的
Unicode 编码或词元字符串本身。

## 字符数据路径

`CharacterData` 用于快速学习和 smoke test。它读取整个文本文件，收集出现过的字符并排序：

```python
chars = sorted(set(text))
stoi = {char: index for index, char in enumerate(chars)}
itos = chars
```

`stoi` 把字符编码成整数，`itos` 按整数取回字符。假设文本只出现 `a`、`b`、换行三个字符，
词表大小就是 3。MDLM 会额外使用编号 3 作为 mask token，但输出词表仍然只有 3 个正常字符。

数据前 90% 作为训练集，后 10% 作为验证集。每次 batch 随机采样起点，并取连续 `T` 个字符：

```text
完整 token 流：  ... 18 4 7 7 2 9 11 3 5 ...
随机起点：                 ↑
一个序列：                 2 9 11 3 5 ... 共 T 个
```

连续窗口保留了文本局部顺序。不要把所有字符独立打乱，否则语言模型将无法学习相邻关系。

## 亲自观察字符 batch

先下载 Tiny Shakespeare：

```bash
mkdir -p data/tinyshakespeare
curl -L https://raw.githubusercontent.com/karpathy/char-rnn/master/data/tinyshakespeare/input.txt \
  -o data/tinyshakespeare/input.txt
```

然后执行：

```bash
python - <<'PY'
import torch
from data import CharacterData

data = CharacterData(
    "data/tinyshakespeare/input.txt",
    block_size=16,
    device=torch.device("cpu"),
)
batch = data.batch("train", batch_size=2, generator=torch.Generator().manual_seed(7))

print("vocab size:", data.vocab_size)
print("shape:", tuple(batch.shape))
print("dtype:", batch.dtype)
for row in batch:
    print("".join(data.itos[token] for token in row.tolist()).replace("\n", "\\n"))
PY
```

你应当看到 shape 为 `(2, 16)`、dtype 为 `torch.int64`，以及两段 16 字符的文本。固定 generator
后重复执行，抽到的窗口应当相同。

## 同一个 batch 如何服务两种目标

数据加载器不提前制造 AR 标签或 MDLM 掩码。它只提供干净序列 `clean: [B, T]`。

AR 在 `train.py` 中做右移：

```python
inputs = clean[:, :-1]   # [B, T-1]
targets = clean[:, 1:]   # [B, T-1]
```

MDLM 在 `diffusion.py` 中保留 `[B, T]`，随机把部分位置换成 mask，并只把这些位置作为目标。

这种分工很重要：两种模型从同一个采样器拿到相同长度的干净数据，差异从 objective 开始，而
不是悄悄藏在两套 data loader 中。

## TinyStories 为什么不用全部读入内存

正式 TinyStories 训练集约 4.74 亿 GPT-2 BPE 词元。若每次启动都解析原始文本并重新分词，
训练不可复现，启动也很慢。`scripts/prepare_tinystories.py` 会：

1. 下载固定 revision 的 parquet 文件；
2. 使用固定的 GPT-2 tokenizer；
3. 在每个文档末尾追加 end-of-text token；
4. 把词元保存为 `uint16` 二进制分片；
5. 在 `manifest.json` 中记录数据版本、tokenizer、分片大小和 SHA-256。

目录类似：

```text
data/tinystories-gpt2/
├── manifest.json
├── train/
│   ├── 00000.bin
│   ├── 00001.bin
│   └── ...
└── validation/
    └── 00000.bin
```

`TokenizedData` 使用 NumPy memory map。操作系统只在访问时把需要的文件页载入内存，不要求
Python 一次复制整个数据集。采样器预先计算每个分片中合法窗口的累计数量，然后把一个全局
随机起点映射到具体分片与局部位置。

## 检查 manifest

准备数据后可以执行：

```bash
python - <<'PY'
import json
from pathlib import Path

path = Path("data/tinystories-gpt2/manifest.json")
manifest = json.loads(path.read_text())
print("format:", manifest["format"])
print("dataset:", manifest["dataset"])
print("tokenizer:", manifest["tokenizer"])
for split, info in manifest["splits"].items():
    print(split, "documents=", info["documents"], "tokens=", info["tokens"])
    print("shards=", len(info["shards"]))
PY
```

正式数据的 manifest 应当明确记录 `roneneldan/TinyStories`、完整 revision、`gpt2` tokenizer 和
`uint16`。如果这些信息不同，就不能声称与仓库报告是完全相同的数据条件。

## 输入词元和监督词元不是同一个数

两种目标都以 `B × T` 统计每 step 的输入词元预算。AR 几乎每个输入位置都有下一个词元标签；
MDLM 只在随机 mask 的位置计算 loss，因此监督 target 数量随 mask ratio 变化。

正式实验固定的是输入词元预算，并同时报告累计监督 target 数量。这样做不宣称是唯一公平定义，
但把重要差异公开记录，后续还可以增加等 FLOPs 或等卡时比较。

## 常见问题

### 字符文件太短

文件至少需要比 `block_size` 多两个字符。流程检查若使用自己的短文本，应降低配置中的
`block_size`，而不是复制同一句话直到看似能运行。

### manifest 中路径存在但分片打不开

manifest 中的分片路径相对于 manifest 所在目录。不要只移动 `manifest.json`；应整体移动
`data/tinystories-gpt2/`。

### 为什么使用 `uint16`

GPT-2 词表大小 50,257，小于 65,536，因此一个词元可以用 16 bit 保存。训练时 batch 会转换为
PyTorch 所需的 `torch.long`。

## 完成检查

- 你能够解释 `[B, T]` 中两个维度的含义；
- 字符 batch 检查能打印两段可读文本；
- 你知道 AR 标签右移和 MDLM 掩码都发生在 data loader 之后；
- 你知道 TinyStories 的版本和 tokenizer 应从 manifest 验证。
