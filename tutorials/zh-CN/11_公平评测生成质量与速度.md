# 11｜公平评测生成质量与速度

训练 loss 不能直接回答“哪个模型生成得更好、哪个更快”。这一章使用仓库的正式评测流水线，
从固定提示生成 10,000 个 continuation，测量性能，并进行隐藏模型身份的成对评审。

## 评测回答的四个问题

1. 在相同 prompt 和采样设置下，AR 与 MDLM 哪个生成质量更好？
2. MDLM 从 8 增加到 64 steps 时，质量如何变化？
3. batch 1、8、32 时，延迟、吞吐和显存分别是多少？
4. 便宜的全量 judge 与更强的抽查 judge 是否一致？

## 前置条件

完整评测默认读取四个 checkpoint：

```text
out/tinystories-106m-ar/best.pt
out/tinystories-106m-mdlm/best.pt
out/tinystories-106m-ar-seed2027/best.pt
out/tinystories-106m-mdlm-seed2027/best.pt
```

还需要完整 manifest：

```text
data/tinystories-gpt2/manifest.json
```

安装依赖：

```bash
python -m pip install -e ".[data,eval,viz]"
```

## 一键正式运行

API key 只放在进程环境，不要写进源码、README 或提交：

```bash
export DEEPSEEK_API_KEY="..."
bash scripts/run_generation_benchmark.sh
```

也可以把 key 放在仓库外的权限文件：

```bash
install -d -m 700 /root/.config/nanodiffusionlab
umask 077
printf 'export DEEPSEEK_API_KEY=%q\n' "$DEEPSEEK_API_KEY" \
  > /root/.config/nanodiffusionlab/judge.env
```

runner 会在 judge 前尝试读取该文件。不要把真实 key 粘贴进终端历史可见的命令文本；可以使用
`read -s` 交互读取。

## 分阶段理解评测

所有阶段写入同一个输出目录，已经完成的 JSONL 会被识别并跳过。

### 阶段一：准备固定提示

```bash
python scripts/benchmark_generation.py \
  --output-dir out/tinystories-106m-generation-eval \
  prepare \
  --num-prompts 1000 \
  --prompt-length 32 \
  --output-length 128 \
  --seed 4242
```

脚本从 validation 文档边界抽取 1,000 个前缀，不让 prompt 跨越 end-of-text。它写出：

- `prompts.jsonl`；
- `evaluation.json`，包含数据、tokenizer、checkpoint、精度、环境与 Git commit。

### 阶段二：四卡生成质量样本

```bash
python -m torch.distributed.run --standalone --nproc_per_node=4 \
  scripts/benchmark_generation.py \
  --output-dir out/tinystories-106m-generation-eval \
  generate \
  --batch-size 8 \
  --steps 8 16 32 64 \
  --temperature 1.0 \
  --top-k 40
```

每个 prompt、checkpoint 和 step 组合都有稳定 seed。记录按 `prompt_id % world_size` 分给 rank，
不同 rank 写自己的 JSONL，不共享文件锁。

样本总数：

```text
2 个 AR checkpoints × 1,000 = 2,000
2 个 MDLM checkpoints × 4 种 steps × 1,000 = 8,000
合计 = 10,000
```

### 阶段三：单卡性能矩阵

```bash
python scripts/benchmark_generation.py \
  --output-dir out/tinystories-106m-generation-eval \
  performance \
  --batch-sizes 1 8 32 \
  --steps 8 16 32 64 \
  --warmup 10 \
  --repeats 30 \
  --device cuda:0
```

性能阶段只用一张 GPU，避免把模型并行或跨卡通信混入解码延迟。每次测量前后显式
`torch.cuda.synchronize`，否则 CPU 计时只会量到异步 kernel 提交时间。

矩阵共 36 行：

- AR：2 seeds × cached/uncached × 3 batches = 12；
- MDLM：2 seeds × 4 step counts × 3 batches = 24。

同时测量完整 continuation 延迟与 first-update latency，并记录 PyTorch peak allocated memory。

### 阶段四：隐藏身份的成对 judge

```bash
python scripts/benchmark_generation.py \
  --output-dir out/tinystories-106m-generation-eval \
  judge \
  --flash-model deepseek-v4-flash \
  --pro-model deepseek-v4-pro \
  --pro-samples 100 \
  --concurrency 32 \
  --max-retries 5
```

每个 MDLM continuation 与同 prompt、同训练 seed 的 AR continuation 配对。A/B 位置由稳定哈希
随机交换，judge 看不到 objective 名称。

Flash 评审全部 8,000 对；Pro 按 8、16、32、64 steps 分层抽取 100 对复核。返回 JSON 必须
通过 winner、五个维度分数范围和字段结构校验，失败会重试。

### 阶段五：统计与作图

```bash
python scripts/benchmark_generation.py \
  --output-dir out/tinystories-106m-generation-eval \
  report
```

输出：

- `summary.json`：完整统计；
- `report.md`：可读表格；
- `quality_latency_frontier.png`：质量–延迟前沿。

## 本地指标是什么作用

外部 judge 可能随模型版本变化，因此还计算无需 API 的透明指标：

- end-of-text 前长度；
- 是否生成 end-of-text；
- unique-token ratio；
- distinct-1/2/3；
- repeated-4-gram ratio。

这些指标不能单独代表故事质量。例如重复率低的随机乱码仍然很差。它们是 guardrail，用来检查
judge 结论是否与明显的重复行为矛盾。

## 如何读 pairwise utility

从 MDLM 视角定义：

- MDLM win = 1；
- tie = 0.5；
- AR win = 0。

utility 0.5 表示双方总体相当，小于 0.5 表示 AR 更常获胜。置信区间通过 prompt-level bootstrap
得到。

参考聚合结果：

| MDLM steps | pairs | MDLM wins | ties | AR wins | utility |
|---:|---:|---:|---:|---:|---:|
| 8 | 2,000 | 5 | 1 | 1,994 | 0.0028 |
| 16 | 2,000 | 21 | 13 | 1,966 | 0.0138 |
| 32 | 2,000 | 65 | 18 | 1,917 | 0.0370 |
| 64 | 2,000 | 140 | 18 | 1,842 | 0.0745 |

Flash 与 Pro 在 100 个抽查 pair 上完全一致率为 98.0%，Cohen's kappa 为 0.960。

## 如何读速度结果

参考 batch-1：

| decoder | latency for 128 tokens | relative to cached AR |
|---|---:|---:|
| cached AR | 0.614 s | 1.00× |
| MDLM 8 steps | 0.045 s | 13.63× faster |
| MDLM 16 steps | 0.093 s | 6.56× faster |
| MDLM 32 steps | 0.175 s | 3.51× faster |
| MDLM 64 steps | 0.348 s | 1.76× faster |

这形成清晰但不理想的前沿：更多 MDLM steps 同时增加质量与延迟；当前 64 steps 仍未接近 AR
质量。结论应写成“当前基线更快但质量明显落后”，而不是“扩散语言模型已经更优”或“永远无效”。

## 为什么 raw 结果不提交 Git

10,000 个 generations 与 8,100 个 API responses 文件较大，并含 provider-specific 内容，默认
留在 ignored `out/`。仓库提交的是精简统计、报告和图片：

- `reports/data/tinystories_106m_generation_eval.json`；
- `reports/tinystories_106m_generation.md`；
- `docs/assets/quality_latency_frontier.png`。

## 完成检查

- `generations/` 中共有 10,000 条唯一记录；
- 每条 continuation 恰好记录 128 个输出 token ids；
- `performance.json` 有 36 行；
- Flash 有 8,000 条、Pro 有 100 条有效 judgment；
- report、summary 和 frontier 图能够生成；
- API key 没有出现在 Git tracked files 中。
